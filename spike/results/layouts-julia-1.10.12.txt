# Phase 0 -- the four delta layouts as dependency declarations
julia = 1.10.12

## 1. Layout selection is already a function of (method, inverse)
   Linearization, no inverse  -> DeltaFnDefaultRuleLayout
   Linearization + inverse    -> DeltaFnDefaultKnownInverseRuleLayout
   Unscented, no inverse      -> DeltaFnDefaultRuleLayout
   Unscented + inverse        -> DeltaFnDefaultKnownInverseRuleLayout

   Note what this shows: `method` and `layout` are ALREADY two axes, and the
   layout is a function of (method, inverse) rather than of the method alone.
   In the new design both collapse into one algorithm VALUE -- the inverse is a
   field of the algorithm, which is why `Linearization{Nothing}` and
   `Linearization{<:Function}` select different rules by ordinary dispatch.
   That is rule 7 vs rule 8 in spike/dispatch/02_rules.jl, and it works.

## 2. The four layouts, written as declarations
   --- default ---
   algorithm = DeltaLinearization / DeltaUnscented
   dependencies = [
       :out      => (m[:ins...],),                    # allbutself is not needed: all ins
       (:in, k)  => (m[:in][k], q[:ins]),             # message on own edge + joint marginal
       :ins      => (m[:out], m[:ins...]),            # the marginal rule over the cluster
   ]

   --- known_inverse ---
   algorithm = DeltaLinearization{HasInverse}
   dependencies = [
       :out      => (m[:ins...],),
       (:in, k)  => (m[:out], m[:ins...] \ k),        # allbutself; NO marginals at all
       :ins      => (m[:out], m[:ins...]),
   ]

   --- cvi ---
   algorithm = DeltaCVI                               # deleted in Phase 6; reference only
   dependencies = [
       :out      => (q[:ins],),                       # NO inbound message on out
       (:in, k)  => (m[:in][k], q[:ins]),             # delegates to default
   ]

   --- cvi_projection ---
   algorithm = DeltaCVIProjection
   dependencies = [
       :out      => (m[:out], q[:out], q[:ins]),      # the only layout consuming q_out
       (:in, k)  => (m[:in][k], q[:ins]),             # delegates to default
   ]

## 3. VERDICT -- the hypothesis HOLDS for input selection, and only for that

   Read across the four, the layouts differ in exactly one respect: which
   messages and marginals each of the four slots consumes. That is a dependency
   declaration, and the table above is it. The ~10 engine calls each layout
   makes are the same calls with different arguments -- repeated wiring, as the
   hypothesis guessed.

   THREE THINGS DO NOT FIT, and they are not dependency choices:

   (a) STATIC GATING. `with_statics` (default.jl:22-44) wraps every outbound
       stream in a combineLatest against const/data inputs, so the node WAITS
       for them, while their values reach the rule out-of-band through the
       function proxy (FixedArguments.fix, delta.jl:184). Measured in
       09_execution.jl: 0 emissions before the static arrives, 2 after. A
       declaration that only names inputs cannot express this. It is execution
       gating and the new design must carry it as its own concept.

   (b) THE N === 1 COMPILE-TIME BRANCH (default.jl:321-327), substituting
       `of(Message(nothing, true, true))` for an empty group. A group selector
       with statically known arity covers this only if the zero-arity case is a
       declared value rather than an empty tuple that stalls the combineLatest.

   (c) `q_out` ALIASING. `deltafn_apply_layout(::Val{:q_out})` (default.jl:47-64)
       connects the local marginal straight to the connected variable's marginal
       stream. That is topology, not a rule input -- nothing computes it.

   CONSEQUENCE FOR THE PLAN: the collapse is real but partial. Dependencies
   absorb the input selection; statics, empty-group arity and marginal aliasing
   need explicit support in MessagePassingRulesBase or they land back in the
   engine. PLAN.md § CVI projection makes CVIProjection-as-an-extension
   conditional on the collapse, and the condition is met for the rules half --
   provided those three are lifted out of the layout and into the language.

   Old CVI is a migration reference only: it is deleted in Phase 6, so its
   declaration above exists to show that the shape fits, not to be built.
