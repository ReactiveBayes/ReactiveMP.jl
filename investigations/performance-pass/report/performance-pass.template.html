ReactiveMP.jl · RxInfer.jl · Rocket.jl · GraphPPL.jl — decision report

ReactiveMP v7 Performance Pass

Before the release, v7 was 1.5–4.6× slower than v6 in steady state and slower to first inference. The losses come from the rule's result being untyped and from a slow activation path, not from the rule system's design. With the changes measured here, including a typed RuleSpec, v7 is faster than v6 in steady state on six of the seven iterative benchmarks, large models included. The belief-propagation models, which are setup-bound, run at 1.25–1.43×. With a precompile workload, the first inference drops from about 9 s to under 1 s. Every change below keeps the posteriors and free energies bit-for-bit identical.

Engine: where the time went

The first profile (iid VMP on HEAD) put 19% of all samples on one line, message.jl:812. _compute_sparams was 13.8% of samples against 1.5% in v6, dynamic dispatch 11.6% and GC 9%. The micro benchmark separates the costs of one rule call, which totalled 873 ns:

  • the rule body itself: 49 ns; resolution: 26 ns, static Julia dispatch as designed;
  • an AfterMessageRuleCallEvent built with nobody listening, its result typed Any: ≈ 300 ns;
  • the Message{D,L} built from that untyped result: ≈ 380 ns;
  • with any callbacks set, two uuid4() span ids: ≈ 760 ns more.

All three have one cause. RuleSpec.body::Function hides the result type, so everything downstream of the body runs on Any. v6 dispatched the rule itself, so its result was inferred.

Two fixes were measured. P3 keeps the spec untyped and adds a function barrier on typeof(spec.body): 69 ns per call. T types the spec: RuleSpec{B, P, S, L, A}. At the engine's call site resolution runs on concrete input types and reaches one rule, so find_message_rule returns one concrete spec, and the body call is static and inlines: 27 ns per call, with 2 allocations (the Message and its AnnotationDict). §3.14 had rejected the typed spec on a toy call site that could reach two rules, where the result is a union of spec types. Engine call sites don't have that shape, and where resolution isn't inferable the call is dynamic in either design. No generated functions or compiler internals are involved.

One MessageMapping call (NMV towards out, BP), in nanoseconds; the number beside each bar is the allocation count. With the typed spec the rule body itself takes 3.8 ns, against 49 ns through the untyped spec.

Activation

Build and activate cost about 25 µs per node on HEAD. Two thirds of it was runtime type construction in the C runtime (lookup_type_setvalue, subtype checks). One function, input_names, accounted for about 33%: it built Any[] vectors and a Val{Tuple(…)} at run time for every interface of every node. The other large cost was alias_interface, whose node argument is a Type that Julia does not specialise on, followed by a linear scan. Caching both halves build and activate time.

JET and the rule registry

After the changes, JET's optimisation analysis of a rule call, a product and a joint marginal reports only the intended barrier, a dynamic as_message per message in a product, and cold warning and error paths. find_message_rule has 234 methods; a fresh resolution compiles in about 2 ms, and the rules package is about 1.2% of first-inference inference time. There is nothing for a custom dispatch to win (see rejected).

First inference

v6 v7 HEAD v7 FULL with the precompile workload

Seconds from a fresh process with packages loaded to the first infer returning. Package load (about 2 s) is not included. None of the five packages had a PrecompileTools workload.

The engine changes by themselves do not move time to first inference: FULL without the workload is within about ±5% of HEAD on nine of eleven models, and the typed spec adds nothing measurable. The workload does move it. Models shaped like the workload become near-instant. The others still gain 29–60%, because the shared machinery (streams, activation, the free energy) arrives precompiled. The precompiled build is also 4–20% faster in steady state than the JIT-compiled one (iid 0.71 → 0.57 ms per iteration, nl 2.26 → 1.87 ms, streaming filter 5.3 → 4.4 ms). The cause wasn't investigated further.

RxInfer's __init__ sends a telemetry ping on a background task by default. It compiles HTTP and JSON on each session's first use, which cost 0–2.5 s of time to first inference, depending on the model. It affects v6 and v7 alike. The report doesn't propose a change; whether to compile that path inside the workload is a policy choice.

Scaling and GC

v6 v7 HEAD v7 FULL

iid VMP: µs per observation per iteration, against n (log scale). A flat line would mean linear scaling.

Every version gets more expensive per observation as the graph grows. v6 does too: 0.65 µs at n = 10³ and 2.2 µs at 10⁵. The cause is GC: each full collection marks the whole live graph.

On HEAD, part of the growth was Rocket's collectLatest, which checked all(vstatus) over every source on every event: O(N²/64) per iteration for the free energy and for a variable's marginal. P7 removes that.

The rest was allocation volume. With the P3 barrier, v7 allocated 13.3 MB per iteration at n = 10⁴ against v6's 7.2 MB. With the typed spec it allocates 9.4 MB, and at n = 10⁴ and 10⁵ it is now faster than v6 (0.86× and 0.94×).

The allocations left per rule call are the Message (mutable, by the §3.19 benchmark) and its AnnotationDict. Per update there are also the DeferredMessage and boxed CountingReals on every free-energy subject.

Rocket, GraphPPL, RxInfer

Rocket

  • The hand-written fast paths (UInt8UpdatesStatus, MStorage1…16) are neither wrong nor faster. Against simple alternatives (an NTuple{N,Bool} or a Vector{Bool} with a counter), runtime is equal for 2–16 sources with zero allocations, because the engine's element types are abstract. Vector{Any} storage compiles 20–35% faster for new source types. Keep them; an abstract-element path is optional.
  • The snapshot in combineLatest costs 36 ns and one 32-byte allocation per emission. It is also the barrier that hands the rules concrete types, so removing it would only move the cost.
  • A subject's actor::Any costs about 1.6 ns of dispatch per listener, and it is the compile-time barrier. Leave it.
  • Subscription takes about 8 KB of stack per chain link: 22 native frames, four of them dynamic LazyObservable crossings. Fewer frames per link would need an engine and Rocket co-design.

GraphPPL

  • For ordinary models GraphPPL is 5–8% of model creation. For ssm1 at n = 10⁴: factor-node construction 30%, activation 41%, the free-energy plugin 17%, GraphPPL's own graph 4.6%.
  • Its two quadratic paths (C1, C6) are the only large GraphPPL wins.
  • Beyond about 3·10⁴ nodes, creation turns superlinear through GC while bytes per node stay constant: ssm1 at 10⁵ takes 22 s, 7 s of it GC.
  • is_factorized blowing up exponentially was ruled out: named := variables carry no links, and all short-circuits.

RxInfer

  • RxInfer's own code is 1.0% of iid VMP, 3.0% of the Kalman smoother and 0.5% of a streaming filter. The per-iteration data feed is already concretely typed.
  • Option costs: session default +1–3%; free_energy = true (Real) against Float64 ≤ 2%; the free energy itself 13–15%; trace = true +26%.
  • There is a floor of about 140 µs and 2 100 allocations per infer, mostly GraphPPL. It matters to code that calls infer in a loop.

Breaking releases of Rocket and GraphPPL

Nothing measured here needs one. Every change worth shipping in Rocket and GraphPPL is non-breaking. The breaking candidates were measured and don't pay for a major release:

  • Rocket, typed listener storage (an actor type parameter on Subject, or FunctionWrappers). FunctionWrappers is 10–25× slower than today's dispatch and depends on llvmcall/cfunction internals. A homogeneous Vector{A} only helps when every listener has the same type, which engine subjects almost never do. It would break ReactiveMP's Subject{M, AsapScheduler, AsapScheduler} and multiply specialisations.
  • GraphPPL, storage redesign (a Vector{NodeData} indexed by counter, typed per-plugin extras, no edge_data). It would gain ≲ 1–2% of creation. It would not break RxInfer, which never reads model.graph, MetaGraphsNext or .extra. It would break GraphPPL's own engine (25 sites), the plotting and GraphViz extensions, and savegraph/loadgraph/prune!.
  • GraphPPL C4 and C5 are soft changes (a different extra container; created_by as an Expr). They could ride along with any future 5.0, but they don't justify one.

If a Rocket 2.0 is ever planned for other reasons, the direction to take is fewer frames per subscription link (typed or flattened message streams, designed together with the engine). That would raise the stack limit further and cut dispatches.

Found on the way

  • RxInfer bug: a, b = infer(…) throws, because iterate(::InferenceResult) reads a :returnval field that doesn't exist. A fix is in the diffs.
  • v6 fails on loopy linear regression (DomainError) and v7 runs it: a behavioural difference worth a line in the migration guide.
  • The engine changes need P9. Without Rocket's stack guard, the 1 000-link chain graph overflows the stack on E4. HEAD handles it, so each link is now a little deeper on the stack.
  • Free-energy setup for deterministic nodes costs about 58 µs per +/* node: loopy linear regression's setup is 15 ms without the free energy and 131 ms with it.
  • The equality chain costs about 10 µs per observation in loopy BP, against about 1 µs for a VMP update. It is linear, not quadratic.
  • The v6 comparison is fair on packages: v6 resolves the same Rocket 1.10.0 and GraphPPL 4.8.0, so every v6-vs-v7 difference comes from the engine.

Method

Variants. Each variant is a set of sibling git worktrees of ReactiveMP, RxInfer, Rocket and GraphPPL with an environment developing them (mkvariant.sh, mkenv.jl):

  • A = HEAD;
  • P12 = P1+P2;
  • E4 = every engine change with the P3 barrier (ENGINE-ReactiveMP.diff);
  • FULL (P3) = E4 plus Rocket P7+P9, GraphPPL C1/C2/C3/C6/C7 and RxInfer P6 with the bug fix;
  • FULL = the same with the typed spec instead of P3 (ENGINE-T-ReactiveMP.diff); what this page reports as FULL;
  • FULL + workload = FULL plus P11;
  • v6 = RxInfer 5.5.2 over ReactiveMP 6.5.0.

Protocol. driver.sh ran 11 models and 6 scaling cases, plus the micro suite, over three rounds: first for v6, HEAD, P1+P2, E4, FULL (P3) and its workload build, then for v6, FULL (P3), FULL and FULL + workload. Every run was a fresh process, the variant order rotated each round, and nothing else ran on the machine. Figures are the median over rounds of each round's minimum. Iterative models are run at I and 2I iterations, so per iteration = (T(2I) − T(I)) / I. Runs use session = nothing and free_energy = Float64, except the +defaults rows.

Correctness gate.

  • Posteriors and free energies, against HEAD: 204 of 204 in the first run and 153 of 153 in the second, all bit-identical.
  • ReactiveMP's root suite on E4, FULL (P3) and the typed spec (with Aqua): 15 339 pass, 6 known broken. On the typed spec, every node package's suite passes, and so does MessagePassingRulesTestUtils (147).
  • MessagePassingRulesBase: 617. StandardMessagePassingRules: 10 139, 1 known broken.
  • GraphPPL: 76 803, 1 known broken. Rocket: 12 295. RxInfer on P6: 14 713.
